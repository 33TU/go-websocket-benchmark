# The full suite, 10k and 30k connections, desktop

Run on 2026-09-17 with this fork at commit 81a59b6: ews v0.2.0, gws v1.10.2,
Go 1.27.1 on Linux 7.2, AMD Ryzen 9 9950X3D. Every framework in
`script/config.sh`, one server at a time pinned to cores 0 to 5, the client
pinned to the other die; 1024-byte payloads, 2,000,000 echoes, then the rate
test for 10 seconds. One run per cell. The generated reports with every
column are in [suite-2026-09-17-9950x3d/](suite-2026-09-17-9950x3d/).

```sh
taskset -c 0-5 ./output/bin/$f.server &
taskset -c 8-15,24-31 ./output/bin/bench.client -f=$f -c=$c -b=1024 -dc=2000 -en=2000000 -rate=true -rd=10 -suffix=_${c}_1024_2000000
./output/bin/bench.client -r=true -suffix=_${c}_1024_2000000
```

## How to read the echo test

The client's echo loop takes a connection from a pool, writes one request,
waits for the reply and returns the connection, so each connection carries
one request at a time and the echo TPS is the connection count divided by
the round trip. The table below is therefore a latency ranking under load,
not a throughput ceiling: at 10k connections 745,000 per second is exactly
10,000 divided by the 13.4 ms median. The servers fall into two latency
groups, one around 13 ms and one around 8 to 9 ms at 10k connections, and
the cause of the gap was not investigated in this run.

## Notes

- ews has the highest EchoEER at both connection counts. At 10k it takes
  the whole offered load with nothing dropped on 204 percent CPU; the three
  other servers that take it all use 340 to 366 percent, and the rest,
  gws included, take 62 percent of it.
- On echo, ews sits with gws, gorilla, fasthttp and quickws in the 13 ms
  group and uses the least memory of that group. The synchronous pair,
  ews_sync and gws_std, ties as before.
- The hertz server ignores SIGTERM; the run needed a SIGKILL to move on.
