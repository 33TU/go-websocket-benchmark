# ews against gws, 10k connections, desktop

Run on 2026-09-17 with this fork at commit ddc02d3: gws v1.10.2, ews v0.2.0,
Go 1.27.1 on Linux 7.2, AMD Ryzen 9 9950X3D, 16 cores. Servers pinned to
cores 0 to 5, six cores on the V-cache die, and the client to the eight
cores and their SMT siblings on the other die, so neither starves the other.
Two runs per server, alternating; both runs are shown. Same method as the
laptop run beside this file, run in the same sitting as the full suite.

```sh
taskset -c 0-5 ./gws.server &
taskset -c 8-15,24-31 ./bench.client -f=gws -c=10000 -dc=2000 -en=2000000 -rate=true -rd=10
```

## BenchEcho

2,000,000 echoes of 1024-byte messages over 10,000 connections.

| server | TPS | CPU avg | memory avg | failed |
|---|---|---|---|---|
| gws | 1,108,325 / 1,094,789 | 366% / 372% | 215 / 201 MB | 0 |
| ews | 1,131,323 / 1,144,614 | 393% / 400% | 143 / 137 MB | 0 |

A tie on throughput and CPU; ews uses less memory, as on the laptop.

## BenchRate

Each connection is offered 200 messages per second for 10 seconds, sent in
16 KiB batches; the client counts what comes back. EchoEER is echoes per
second per CPU percent.

| server | EchoEER | sent | received | dropped | CPU avg | memory avg |
|---|---|---|---|---|---|---|
| gws | 5,742 / 5,743 | 19.90M / 19.90M | 19.90M / 19.90M | 0.0% / 0.0% | 347% / 347% | 218 / 217 MB |
| ews | 10,328 / 10,266 | 19.90M / 19.90M | 19.90M / 19.90M | 0.0% / 0.0% | 193% / 194% | 168 / 178 MB |

On this machine both servers take the whole offered load of 20M messages,
so the difference is CPU: ews answers the same messages on a little over
half of gws's, 1.8 times the efficiency per CPU point, the same
ratio as on the laptop where gws could not keep up and dropped.

## Synchronous pair: gws_std against ews_sync

Both through net/http on every port, both writing each echo before the next
read, both handing the connection to a fresh goroutine and returning from the
handler. Same machine and method as above, two runs each.

| server | echo TPS | echo CPU | echo memory | rate EER | sent | dropped | rate memory |
|---|---|---|---|---|---|---|---|
| gws_std | 1,160,224 / 1,165,214 | 393% / 392% | 160 / 158 MB | 5,835 / 5,862 | 19.90M / 19.90M | 0.0% / 0.0% | 193 / 199 MB |
| ews_sync | 1,162,241 / 1,174,277 | 388% / 388% | 156 / 147 MB | 6,075 / 6,085 | 19.91M / 19.90M | 0.0% / 0.0% | 156 / 147 MB |

A tie, as on the laptop. The asynchronous ews server's lead is the Queue
coalescing a backlog into one writev, not the read side.

This file replaces a run from earlier the same day that measured the
machine in a slower state, where gws took 62 percent of the offered load
and the ratio read 2.5; see the note in the full suite results.
