# ews against gws after ews PR #10, 10k connections, desktop

Run on 2026-09-26 with this fork pinned to ews v0.4.1, whose only change
over v0.4.0 is the merge of
[ews PR #10](https://github.com/33TU/ews/pull/10) (large-message read path,
size-class buffer pool), against gws v1.10.2; Go 1.27.1 on Linux 7.2, AMD
Ryzen 9 9950X3D. Same method and pinning as the
[2026-09-17 run](ews-vs-gws-2026-09-17-9950x3d.md): servers on cores 0 to 5,
the client on the other die, one run per cell. Only the ews servers and gws
were rerun; the other frameworks did not change. Two sittings twenty minutes
apart, ews with gws and then ews_sync, each with a gws run before its first
cell and after its last as a drift check. The generated reports are in
[ews-vs-gws-2026-09-26-9950x3d/](ews-vs-gws-2026-09-26-9950x3d/), the drift
runs under their own suffixes.

```sh
taskset -c 0-5 ./output/bin/$f.server &
taskset -c 8-15,24-31 ./output/bin/bench.client -f=$f -c=10000 -dc=2000 -b=1024 -en=2000000 -rate=true -rd=10 -suffix=_10000_1024_2000000
taskset -c 8-15,24-31 ./output/bin/bench.client -f=$f -c=10000 -dc=2000 -ec=10000 -b=262144 -en=200000 -suffix=_10000_262144_200000
```

## BenchEcho, 10,000 connections, 256 KiB payloads

200,000 echoes with one message in flight per connection, 2.5 GB in flight
against a 4.2 GB/s loopback link, so the link is the ceiling and the means
and tails are queueing in front of it; read the CPU and memory columns.

| server | TPS | TP50 | avg | TP99 | CPU avg | memory avg | 2026-09-17 |
|---|---|---|---|---|---|---|---|
| ews | 16,375 | 8.47ms | 589ms | 7.63s | 156% | 151 MB | 16,384, 10.1ms, 175%, 147 MB |
| ews_sync | 16,649 | 7.28ms | 558ms | 7.98s | 135% | 160 MB | 16,786, 6.5ms, 146%, 156 MB |
| gws | 13,470 | 15.78ms | 725ms | 6.68s | 405% | 321 MB | 13,294, 16.6ms, 408%, 310 MB |

Drift checks, gws after the last cell of each sitting: 13,439 and 13,462 TPS
at 420 and 417 percent CPU.

The one movement is the ews servers' CPU at 256 KiB, 175 to 156 percent for
ews and 146 to 135 for ews_sync at the same throughput, with ews's median
round trip down from 10.1 to 8.5 ms. That is the
read path of PR #10: a single-frame message is now gathered with one
reservation from the frame header instead of growing into place, and the
buffer goes back to a size-class pool. A 256 KiB message sits below the
1 MiB pool cap either way, so the memory column does not move; the PR's
larger effect is on messages past that cap, which this harness does not
send.
