# ews against gws over TLS, 10k connections, desktop

Run on 2026-09-17 with this fork at commit 172bc42, the servers started
with `-tls` and the client with `-tls`: a self-signed certificate from
`cmd/gencert`, crypto/tls on the servers, nbio's TLS on the client, no
verification. Same machine, pinning and method as the plain desktop files
beside this one. Echo only: the harness's rate test hands each connection
to nbio's poller, which takes raw sockets and refuses the TLS wrapper, so
under TLS the client exits before the rate phase. The gws drift check read
812,424 echoes per second before the sequence and 816,798 after.

```sh
taskset -c 0-5 ./output/bin/gws.server -tls &
taskset -c 8-15,24-31 ./output/bin/bench.client -tls -f=gws -c=10000 -dc=2000 -en=2000000
```

## BenchEcho, 1 KiB, 10,000 connections

Two alternating runs per server. For comparison, plain on the same day:
ews 1,131k and 1,145k, gws 1,108k and 1,095k, on 366 to 400 percent CPU and
137 to 215 MB.

| server | TPS | TP50 | CPU avg | memory avg |
|---|---|---|---|---|
| gws | 815,000 / 822,885 | 11.82ms / 11.69ms | 451% / 447% | 362.52M / 404.28M |
| ews | 842,282 / 844,661 | 11.41ms / 11.50ms | 447% / 448% | 377.11M / 344.50M |
| ews_sync | 868,046 / 843,765 | 11.02ms / 11.07ms | 439% / 413% | 298.55M / 304.29M |

TLS takes about a quarter off everyone's echo rate and adds about 80
percent CPU and 200 MB, the record buffers of 10,000 connections, to
everyone alike. What is left separates by a few percent: ews and gws tie
within three, ews_sync is a little ahead on the least CPU. The client's own
CPU was the same for every server, about 32 CPU-seconds per run.

## BenchEcho, 256 KiB, 10,000 connections

One message in flight per connection, 200,000 echoes. Plain on the same
day: ews 16,384, gws 13,294, ews_sync 16,786 echoes per second.

| server | TPS | TP50 | TP99 | CPU avg | memory avg | client CPU |
|---|---|---|---|---|---|---|
| gws | 9,372 | 24.16ms | 8.37s | 297% | 1.32G | 1281% |
| ews | 10,394 | 72.26ms | 7.01s | 185% | 1.16G | 1302% |
| ews_sync | 10,969 | 22.41ms | 7.53s | 237% | 1.16G | 1244% |

Encryption lowers the ceiling from 4.2 GB/s each way to about 2.5 to 2.8,
and the client, which now decrypts and re-encrypts that at 7 cores, is
close to being the limit. The memory column levels out: the 147 MB against
310 MB of the plain run becomes 1.16 GB against 1.32 GB once each
connection carries TLS record buffers. ews still moves the bytes on the
least CPU, 185 percent against gws's 297, and ews_sync on 237.

The medians here, 24, 72 and 22 ms, say nothing about the servers. With
10,000 messages in flight against a link that carries about 10,000 echoes a
second, the mean round trip is close to a second for every server, as
Little's law requires: 1.05 s for gws, 0.94 s for ews, 0.89 s for ews_sync.
The distributions are therefore extremely skewed and the median only
reflects the order in which a server happens to serve its connections. The
Queue path has the higher median and the better tail, 4.7 s against 4.8 s
at TP90 and 7.0 s against 7.5 s at TP99, because its writer goroutine hands
service around more evenly; the synchronous path favors whichever
connection's goroutine wakes first. At 1,000 connections over TLS, where
the link is not oversubscribed, the two paths measure the same to the
millisecond: 55 ms median, 116 ms TP90, 250 ms TP99, on the same CPU.

| gws | 12,441 | 80.18ms | 68.92ms | 122.61ms | 316.67ms | 625.93ms | 428% | 1.49G |
| ews | 14,852 | 67.17ms | 59.85ms | 103.16ms | 186.97ms | 513.89ms | 306% | 875.05M |
| ews_sync | 15,156 | 65.83ms | 60.93ms | 104.44ms | 175.92ms | 393.63ms | 306% | 863.02M |

gws's TP99 is 1.7 times the others' and its worst echo 1.6 times, on 40
percent more CPU and 70 percent more memory. ews and ews_sync are the same
server here to within noise.

## Notes

- `-tls` is wired for gws, gws_std, ews and ews_sync. Their pid endpoints
  moved to a plain port beside the WebSocket ports so the client can still
  read them over HTTP. The other frameworks serve the pid on a WebSocket
  port and would need the same change.
- The rate test under TLS needs the client's connection registration to
  unwrap the TLS conn and feed the poller through nbio's non-blocking TLS
  layer, as its HTTP client does internally.
