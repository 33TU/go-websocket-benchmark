# ews against gws over TLS with the rate test, 10k connections, desktop

Run on 2026-09-27 with this fork pinned to ews v0.4.2, gws v1.10.2, Go
1.27.1 on Linux 7.2, AMD Ryzen 9 9950X3D. Servers and client started with
`-tls`: a self-signed certificate from `cmd/gencert`, crypto/tls on the
servers, nbio's non-blocking TLS on the client, no verification. Servers
pinned to cores 0 to 5, the client to the other die, one run per cell, one
sitting, gws before the first cell and after the last as a drift check.

This is the first TLS run with the rate test. The
[2026-09-17 TLS file](tls-2026-09-17-9950x3d.md) is echo only, because the
rate phase hands each connection to nbio's poller and a `crypto/tls`
connection has no descriptor to hand it. The client now redials those
connections through nbio's own websocket dialer, which wraps a non-blocking
connection in llib's TLS and leaves the TLS connection as the one the rate
phase writes its batches to, so they are encrypted rather than bypassing
the record layer. The redial happens between the echo and rate phases,
outside both timed windows; 10,000 connections take well under a second.
The plain path is unchanged, so the plain files beside this one stay
comparable.

```sh
taskset -c 0-5 ./output/bin/$f.server -tls &
taskset -c 8-15,24-31 ./output/bin/bench.client -tls -f=$f -c=10000 -dc=2000 -b=1024 -en=2000000 -rate=true -rd=10
taskset -c 8-15,24-31 ./output/bin/bench.client -tls -f=$f -c=10000 -dc=2000 -ec=10000 -b=262144 -en=200000
```

## BenchRate, 10,000 connections, 1024-byte payloads

Each connection is offered 200 messages per second for 10 seconds in 16 KiB
batches, and the client stops writing to a connection that is more than
five batches behind, so a server that cannot keep up is sent less rather
than queued at. EchoEER is echoes per second per CPU percent.

| server | EchoEER | sent | received | dropped | CPU avg | memory avg |
|---|---|---|---|---|---|---|
| ews | 5,833 | 19.90M | 19.90M | 0.0% | 341% | 590 MB |
| ews_sync | 4,439 | 19.51M | 19.39M | 0.6% | 437% | 680 MB |
| gws | 4,302 | 19.25M | 19.16M | 0.5% | 445% | 738 MB |

Drift check, gws before the first cell: 4,286 EchoEER at 446 percent CPU.

Only ews takes the whole offered load of 19.9M messages with nothing
dropped, and it does so on a hundred CPU points less than the other two,
1.36 times gws's echoes per CPU point. The plain run on this machine is
1.8 times, with every server taking the whole load; TLS narrows the ratio
because encryption is a cost none of them can avoid, and at the same time
puts gws and ews_sync over the line where the client has to throttle them.
The shape is the same as plain: the Queue coalesces a connection's backlog
into one writev, and the synchronous server, which writes each echo before
the next read, sits with gws.
